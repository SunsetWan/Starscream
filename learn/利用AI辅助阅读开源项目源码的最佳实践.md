以下是利用 AI 辅助阅读开源项目源码的最佳实践：

---

## 1. 先建立全局认知，再深入细节

**不要一上来就逐文件阅读。** 先让 AI 帮你建立项目的整体架构图：

```
"帮我梳理这个项目的目录结构和模块划分，画一张架构图"
"这个项目的核心数据流是怎样的？"
```

以 Starscream 为例，你可以先问："从 `socket.connect()` 到收到 `.text` 事件，经过了哪些模块？" 这比逐个文件看高效得多。

## 2. 带着问题读，而不是漫无目的地读

最有效的方式是 **从一个具体行为出发，追踪调用链**：

```
"WebSocket 的握手过程是在哪里实现的？带我走一遍代码流程"
"收到一个 binary frame 后，数据是怎么被解析和分发的？"
"disconnect 时的 close handshake 是如何符合 RFC 6455 的？"
```

这种方式让你沿着执行路径理解代码，而不是迷失在文件列表中。

## 3. 让 AI 解释设计决策，而非仅仅解释语法

好的问题：
```
"为什么作者要把 Transport 抽象成协议而不是直接用 URLSessionWebSocketTask？"
"这里用 enum 而不是多个 delegate 方法，有什么好处？"
"FrameCollector 和 Framer 为什么要分开？"
```

差的问题：
```
"这行 Swift 代码是什么意思？"  ← 太基础，查文档更快
```

## 4. 利用 AI 做"对照阅读"

将代码与规范对照：
```
"RFC 6455 Section 5.2 定义的 frame 格式，对应到 Starscream 的代码是哪里？"
"Autobahn 测试用例 6.x（UTF-8 校验）在代码中是如何处理的？"
```

将不同项目对照：
```
"Starscream 和 URLSessionWebSocketTask 在处理 ping/pong 上有什么区别？"
```

## 5. 逐层深入的阅读节奏

```
第1轮：目录结构 + 入口文件 → 理解"有什么"
第2轮：核心流程追踪 → 理解"怎么跑"
第3轮：边界情况 + 错误处理 → 理解"怎么保证健壮性"
第4轮：设计模式 + 扩展点 → 理解"为什么这样设计"
```

每一轮都可以让 AI 辅助总结和画图。

## 6. 让 AI 生成可视化

```
"画一张 WebSocket 连接生命周期的状态机图"
"画一张 frame 解析的时序图"
```

一张图往往比读十个文件更有效。

## 7. 实用技巧

| 技巧 | 说明 |
|------|------|
| **克隆到本地** | 让 AI 直接读源码，比贴代码片段准确得多 |
| **从测试读起** | 测试用例是最好的使用文档，问 AI "这个测试在验证什么行为" |
| **记笔记** | 让 AI 帮你生成阅读笔记或 Markdown 总结，方便回顾 |
| **质疑 AI** | AI 可能会编造调用关系，关键结论让它给出具体文件和行号 |
| **分次阅读** | 每次聚焦一个模块，不要试图一次理解整个项目 |

---

**核心原则：AI 最擅长帮你"连点成线"—— 你负责提出好问题，它负责追踪代码、整理关系、可视化结构。** 把 AI 当作一个随时可以回答问题的"结对阅读伙伴"，而不是一个被动的翻译器。
